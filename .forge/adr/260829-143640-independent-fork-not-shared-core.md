# VS Code 확장과 코드를 공유하지 않고 독립 포크로 간다

`gyuha/vscode-3d-model-lens` 의 뷰어 코드를 이 저장소로 **복사해 오고, 이후 두 저장소는 각자 진화한다.**
공유 core 패키지도, 서브모듈도, 모노레포도 만들지 않는다.

## 맥락

원본은 4,730줄이고 그중 뷰어 본체(`src/webview/*` + 순수 로직)가 약 2,900줄이다. 이 부분은 순수 브라우저
코드이므로 "공유 패키지로 떼어내면 한 번만 고치면 된다"는 유혹이 크다. 실제로 그 유혹은 타당하다 —
뷰어 버그를 앞으로 두 곳에서 각각 고쳐야 한다.

그런데 실측해 보면 뷰어는 순수하지 않다. VS Code 테마 CSS 변수 `--vscode-*` 가 18종 45곳에 박혀 있고,
HTML 은 `cspSource` 와 `asWebviewUri` 를 주입받아 런타임에 문자열로 조립되며, 호스트와의 대화는
`acquireVsCodeApi` 를 전제한 `postMessage` 프로토콜이다. 공유 패키지를 만들려면 이 결합을 **원본
저장소에서 먼저 걷어내는 대규모 리팩터링**이 선행돼야 한다. 그것은 "Tauri 앱으로 만들어 달라"는 요청의
범위를 훨씬 넘고, 아직 배포 중인 확장을 흔든다.

## 결정

독립 포크. 대가는 명시적으로 받아들인다 — **뷰어 버그는 두 번 고쳐야 한다.**

그 대신 얻는 것: 원본 확장은 손대지 않아도 되고, 데스크톱 쪽은 VS Code 결합을 걷어내는 작업을
리팩터링이 아니라 **이식**으로 처리할 수 있다. 이식은 결과를 눈으로 확인하며 진행할 수 있지만,
살아 있는 확장의 리팩터링은 그렇지 않다.

## 결과

- 원본의 `.forge/CONTEXT.md` 와 ADR 10개를 이 저장소로 함께 가져왔다. 결정의 근거가 코드와 같이 와야
  다음 사람이 "왜 이렇게 돼 있지"를 물을 곳이 생긴다.
- 그중 VS Code 를 전제한 것들은 여기서 무효이거나 다른 메커니즘으로 대체된다 —
  각 ADR 에 `amended` 줄로 표시했다.
- 두 저장소의 뷰어가 갈라지기 시작하는 순간부터 이 결정의 비용이 실제로 발생한다. 그 시점에
  공유 core 를 다시 검토하는 것은 정당하다. 지금 미리 만드는 것이 정당하지 않을 뿐이다.
